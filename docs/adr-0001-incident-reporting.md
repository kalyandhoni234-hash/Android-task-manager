# ADR-0001 — Automated Incident Reporting (investigation artifact, not verdict)

Status: Accepted
Date: 2026-08-15

## Context

The tool already collects a rich, structured picture of a device over time:
baseline snapshots, drift checks, heuristic suspicious signals, per-package
permission audits, socket-table reads and process samples. That data lives in
GUI memory only: a user who saw "2 change(s) detected" or a HIGH signal had no
way to capture *what happened*, *when*, and *which evidence it rests on* into
a shareable artifact.

The goal is an **automated incident report**: one deterministic document that
aggregates everything the monitoring session observed into findings, evidence
rows, a timeline, severity counts and investigation recommendations, and that
can be exported as JSON, HTML and PDF.

## Decision

A new GUI-independent `incident` layer (`src/android_task_manager/incident/`)
with three pure modules — `models.py` (schema), `builder.py` (aggregation),
`renderers.py` (JSON/HTML) — plus a GUI-only PDF writer and an export worker.

**The report is an investigation artifact, not a verdict.** It records facts
(drift events, observed in the diff engine's own wording), findings (existing
signal/flag vocabulary), and interpretation (a summary and *investigation*
recommendations). It never concludes "malware", "compromised", or "should be
removed", and never recommends remediation — no uninstall/disable/kill/delete
language exists anywhere in the report texts.

## Consequences

### Why no LLM

The report is generated by deterministic aggregation code. An LLM would
introduce non-determinism, hallucinated entities/timestamps, verdict pressure,
and prompt/pipeline complexity — all contrary to the project's "no fabricated
data" invariant. The wording in the report is always the existing analysis
layers' own wording, preserved verbatim.

### Read-only guarantees

`builder.py` and `renderers.py` are pure functions: no I/O, no ADB, no shell,
no network, no GUI state. They cannot modify the device by construction (they
do not even import the machinery for it — enforced by tests). Report
generation runs on the GUI thread (fast, pure); only file exports run on a
worker thread, matching the BaselineWorker conventions.

### Severity semantics stay within the existing vocabulary

Severities are only the existing `HIGH` / `MEDIUM` (heuristics) and `INFO`
(diff engine). Permission combination flags map to **INFO** findings: the
permission analyzer's model is informational framing ("worth reviewing"), and
re-labeling it MEDIUM would invent a severity the analyzer never claimed. The
`low` count is a reserved schema key, always 0 (the project has no LOW
severity). The assessment line is derived deterministically: any HIGH →
`REVIEW REQUIRED`, MEDIUM → `REVIEW RECOMMENDED`, INFO-only → `INFORMATIONAL`,
empty → `NO SIGNIFICANT FINDINGS`.

### The timeline never fabricates timestamps

Every timeline entry carries a real input timestamp (baseline creation, drift
check's `compared_at`, heuristic evaluation, audit read). Drift events are
dated by the drift check that reported them — that is when they became known.
None-null timestamps sort last; ties are broken by a fixed event-type rank.

### Unavailable is never zero

`None` serializes as JSON `null` and renders as "Unavailable" in HTML; a real
`0.0` metric stays `0.0`. Enrichment (socket state, process metrics, package
association) is applied only from real snapshots when supplied, and socket
package association uses the network investigation's UID→package map (falling
back to snapshot data) — never a guess.

### Integrity, not forensics

Each report carries `evidence_sha256`: the stdlib SHA-256 of the canonical
JSON payload (everything except the integrity section). It detects accidental
change during transport/copying; the report states that it is not forensic
immutability. Report IDs are deterministic (`ATM-YYYYMMDD-NNN`).

### PDF is a GUI-layer rendering

The project has no PDF infrastructure outside PySide6's GUI extra, so PDF
writing lives in `gui/incident_pdf.py` using `QPdfWriter` + `QTextDocument`
fed the same `html_report()` output — one rendering source, three formats.
Qt applies its own CSS subset, so the PDF approximates the HTML view; PDF
bytes are inherently Qt-dependent (non-deterministic across Qt versions),
which is documented.

### Extensibility

New evidence sources attach by adding evidence rows and `related_*` reference
resolution; new recommendation texts extend the fixed `_RECOMMENDATIONS` map.
The JSON schema is versioned (`schema_version`).

## Alternatives considered

- **Natural-language LLM summary** — rejected (see above).
- **Report generation on a worker thread** — rejected: the build is pure and
  microseconds-fast; only file writes need a thread.
- **PDF via reportlab / weasyprint** — rejected: new dependency; the GUI extra
  already ships Qt's PDF writer.
- **Screenshots or GUI-state dumps** — rejected: not machine-readable, not
  deterministic, not GUI-independent.
